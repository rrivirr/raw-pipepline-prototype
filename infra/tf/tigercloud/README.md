# tigercloud

Terraform configuration for the `sensor-ingest` TimescaleDB service on TigerData
Cloud, per `../prompts/generate-tigercloud-terraform.md`.

## What it creates

One `timescale_service` named `sensor-ingest` at 500 milli-CPU / 2 GiB memory —
the smallest supported compute tier — in `us-east-1`.

## Prerequisites

- Terraform `~> 1.11`. The configuration itself only needs 1.9+ (cross-variable
  `validation`); the floor is set higher so `password_wo` is available if
  credential management moves into Terraform later.
- TigerData client credentials: console → project name (upper left) →
  **Project settings** → **Create credentials**. The project ID is shown under
  the same project menu.

## Usage

```bash
cp terraform.tfvars.example secrets.tfvars   # fill in real values
terraform init
terraform fmt -check -recursive
terraform validate
terraform plan -var-file=secrets.tfvars -out=tfplan
terraform apply tfplan
```

Apply the saved `tfplan` rather than re-running `plan` inside apply, so what you
reviewed is what executes.

Connection details afterwards:

```bash
terraform output
```

The Postgres password is generated by TigerData and is not exposed as an output.
Retrieve it from the console, or set `password_wo` / `password_wo_version` on the
resource if you want Terraform to own it.

## Sizing: why there is no storage argument

The spec asks for "0.5 CPU and 2 GiB memory" for compute *and storage*. There is
nothing to set for storage. TigerData moved to usage-based storage in June 2023 —
you are billed for what you actually store, and the provider's `storage_gb`
argument is **deprecated**. Emitting it would be dead configuration, so it is
omitted. The compute pair fully expresses the requested size.

Supported tiers, enforced by `validation` in `variables.tf`:

| milli_cpu | memory_gb |
|---|---|
| 500 | 2 |
| 1000 | 4 |
| 2000 | 8 |
| 4000 | 16 |
| 8000 | 32 |
| 16000 | 64 |
| 32000 | 128 |

## Assumptions

- **Region `us-east-1`.** The spec names no region, and one is required for a
  non-replica service. Override with `region_code`.
- **No HA replica, no connection pooler, no VPC.** None were requested; each
  adds cost.
- **Provider-generated password.** Keeps the secret out of a `.tfvars` file. It
  still lands in state — see below.

## Local state: the tradeoff

The spec requires a local backend, so that is what is configured. This is a
deliberate deviation from normal practice, and the consequences are real:

- No locking, no encryption, no versioning, no audit trail.
- `terraform.tfstate` contains the service password and hostname in cleartext.
- Not safe for more than one operator.

`.gitignore` excludes `*.tfstate*` and `*.tfvars`. Back the state file up before
any apply — it is the only record of what exists. Moving to a remote backend
later is `terraform init -migrate-state` after adding a `backend "s3"` block.

## Validation status

Not run. No Terraform runtime is installed in this environment (`terraform`,
`tofu`, `tflint`, `trivy`, `checkov` all absent), and `plan` additionally
requires live TigerData credentials. The commands above are the ones to run;
treat the configuration as unvalidated until they pass.

## Rollback

`terraform destroy` deletes the service **and its data**. Before running it:

```bash
terraform plan -destroy -var-file=secrets.tfvars
```

Review every resource listed, keep the plan output as evidence, and never use
`-auto-approve`. Restoring afterwards means a fresh apply plus a data reload —
the service is not recoverable from state alone.
